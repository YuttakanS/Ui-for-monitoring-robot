## 1. ภาพรวม: ทุกรอบทำ 4 ขั้น (เหมือนกันทั้งสองชุด)

```
photodiode ×3 ──ADC 25 kHz──▶ [1] เก็บสัญญาณ 2500 ตัวอย่าง (0.1 s)
                                    │
                                    ▼
                              [2] demodulate (lock-in)
                                  แยกแสงของ LED แต่ละดวงตามความถี่
                                  ได้ RSS = จำนวน LED × 3 ค่า
                                    │
                                    ▼
                              [3] EKF: predict → ทำนาย RSS จากแบบจำลอง → correct
                                    │
                                    ▼
                              [4] พิมพ์ "Quadrant n: x, y, deg[, z]"
```

### [1] เก็บสัญญาณ
timer ทำงานทุก 40 µs (= 25 kHz, `samplingFreq`) และอ่าน `analogRead()` ของขา GP28, GP27, GP26 (`pins`) ซึ่งเป็น photodiode 0, 1, 2 ตามลำดับ ADC เป็นแบบ 10 bit จึงได้ค่า 0–1023 แต่ละช่วงยาว `N = 2500` ตัวอย่าง = 0.1 s

### [2] Demodulation แบบ lock-in
LED แต่ละดวงกระพริบที่ความถี่ของตัวเอง (`Fref`) photodiode จึงเห็นแสงจากทุกดวงซ้อนกัน วิธีแยกคือคูณสัญญาณด้วย sin และ cos ที่ความถี่ของ LED ดวงที่สนใจ แล้วรวมกันทั้งช่วง

```
S = Σ x[i]·sin(2π·f·i/fs)     C = Σ x[i]·cos(2π·f·i/fs)
RSS = √(S² + C²) / N
```

- องค์ประกอบที่ความถี่ตรงกับ `f` จะรวมกันเป็นค่าใหญ่ ส่วนความถี่อื่นจะหักล้างกันเป็นศูนย์ เพราะช่วง 0.1 s ทำให้ความถี่ที่ห่างกันเป็นพหุคูณของ 10 Hz ตั้งฉากกัน และความถี่ของ LED ทุกดวงห่างกันเป็นพหุคูณของ 100 Hz
- แสงคงที่ (DC) เช่น ไฟห้อง ก็หักล้างไปด้วยเหตุผลเดียวกัน
- ที่ใช้ทั้ง sin และ cos ก็เพราะไม่รู้เฟสของ LED แต่ √(S² + C²) ไม่ขึ้นกับเฟส

### [3] EKF (Extended Kalman Filter)

**State** (ชุดแรกมี 6 ค่า ปัจจุบันมี 8 ค่า):

| index | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| ค่า | x | vx | y | vy | θ | ω | z | vz |
| หน่วย | m | m/s | m | m/s | rad | rad/s | m | m/s |

index 6–7 มีเฉพาะในชุดปัจจุบัน ส่วนในโค้ดใช้ชื่อ `IX = 0, IY = 2, ITH = 4, IZ = 6`

**Predict:** ใช้แบบจำลองความเร็วคงที่ ตำแหน่งใหม่ = ตำแหน่งเดิม + T × ความเร็ว
```
x̂⁻ = A·x̂        A = เมทริกซ์ทแยงเป็น 1 และมี T อยู่ที่ (ตำแหน่ง, ความเร็ว) ของแต่ละคู่
P⁻ = A·P·Aᵀ + Q
```

**แบบจำลองการวัด (สำคัญที่สุด):** ทำนายว่าถ้าหุ่นอยู่ที่ x̂⁻ แล้ว photodiode `l` ควรวัดแสงจาก LED `k` ได้เท่าไร

```
h_kl = (m+1) · cos^m(φ) · cos(ψ) / d²     (ถ้า ψ อยู่นอก FoV ให้เป็น 0)
```
- `d` คือระยะจาก photodiode ถึง LED
- `φ` คือมุมที่แสงออกจาก LED วัดจากแกนที่ชี้ลงพื้น (`uk = (0, 0, −1)`) แบบ Lambertian ลำดับ `m = 1`
- `ψ` คือมุมที่แสงตกบน photodiode วัดจาก normal ของ PD
- normal ของ PD ตัวที่ `l` คือ `v_l = (cos be·cos al_l, −cos be·sin al_l, sin be)` โดย `al` = 0°, 120°, −120° คือทิศรอบตัวหุ่น ส่วน `be` คือมุมเงยจากพื้น จากนั้นหมุนตาม θ ด้วย `Omega0 = R(−θ)`
- ค่าคงที่อื่น เช่น (m+1)/2π และพื้นที่ของ PD รวมอยู่ใน γ แล้ว

แบบจำลองเต็มของค่า RSS:
- ชุดแรก: `RSS_kl = γ_k · h_kl`
- ปัจจุบัน: `RSS_kl = γ_k · PD_GAIN_l · h_kl + RSS_OFFSET`

**Jacobian:** หาเชิงตัวเลข โดยขยับ state แต่ละตัวไป ±`eps` (0.01) แล้วดูว่า RSS ที่ทำนายเปลี่ยนเท่าไร
```
J[i][j] ≈ (RSS(x + eps) − RSS(x − eps)) / (2·eps)
```
คิดเฉพาะคอลัมน์ x, y, θ (และ z ในชุดปัจจุบัน) เพราะ RSS ไม่ขึ้นกับความเร็ว

**Correct:**
```
K = P⁻·Jᵀ·(J·P⁻·Jᵀ + R)⁻¹
x̂ = x̂⁻ + K·(RSS ที่วัด − RSS ที่ทำนาย)
P = (I − KJ)·P⁻·(I − KJ)ᵀ + K·R·Kᵀ      (Joseph form ซึ่งเสถียรกว่า)
```
`R` เป็นเมทริกซ์ทแยงที่มีค่า `sigma2 = 0.01` ทุกช่อง

**LED ที่ปิดอยู่:** ตั้ง RSS ที่ทำนายให้เท่ากับค่าที่วัด และตั้งแถวของ Jacobian เป็น 0 LED ดวงนั้นจึงไม่มีผลต่อการ correct

### [4] Output
```
Quadrant <n>: <x cm>, <y cm>, <θ องศา>[, <z cm>]
```
n คือ quadrant ตามเครื่องหมายของ x, y ส่วน `mode` 1 = พิมพ์ RSS ดิบ, 2 = พิมพ์พิกัด (ค่าเริ่มต้น), 3 = พิมพ์ทั้งสองอย่าง บรรทัดที่ขึ้นต้นด้วย `#` เป็นข้อความสถานะ หน้าเว็บจะข้ามไป

## 3. รายละเอียดแต่ละเรื่อง (โค้ดเก่า → ใหม่)

### 3.1 การเก็บสัญญาณ: เก็บให้ครบก่อน → ring buffer

**เก่า:** `loop()` สั่งเริ่มเก็บแล้วรอจนครบ 2500 ตัวอย่าง (100 ms) ระหว่างนั้น CPU ไม่ได้ทำอะไร
```cpp
sampleIndex = 0;
isSampling = true;
while (isSampling) { }   // รอ 100 ms
```

**ใหม่:** timer เขียนลง `ring[3][5000]` ตลอดเวลา และ `loop()` รอแค่จนมีตัวอย่างใหม่ครบ `UPDATE_EVERY = 1250` ตัว (50 ms) แล้วคำนวณ 2500 ตัวล่าสุด
```cpp
bool timer_callback(...) {
  ring[g][ringWrite] = analogRead(pins[g]);   // ทั้ง 3 ตัว
  ringWrite = (ringWrite + 1) % RING_N;
  sampleCount++;
}
```

```
เวลา →  |----2500----|
              |----2500----|          ช่วงซ้อนกัน 50%
                    |----2500----|    ได้ค่าใหม่ทุก 50 ms
```

- noise ต่อค่าเท่าเดิม เพราะแต่ละค่ายังเฉลี่ยจากสัญญาณ 0.1 s แต่ค่าที่ติดกันใช้ข้อมูลซ้อนกันครึ่งหนึ่ง จึงไม่อิสระต่อกัน
- ring มีขนาด 2N คำนวณจากช่วงที่หยิบมาได้ไม่เกิน 100 ms ก่อนที่ข้อมูลเก่าสุดจะถูกเขียนทับ ซึ่งตอนนี้ใช้จริงราว 19 ms
- ระหว่างรอ `loop()` จะเรียก `wifiPoll()` เพื่อตอบ WiFi ไปด้วย

### 3.2 Demodulation: `sin()` แบบ float → ตารางจำนวนเต็ม

**เก่า:** เรียก `sin()` และ `cos()` 2500 × 3 ครั้งต่อ LED
```cpp
angle = 2.0f * M_PI * Fref[f] * i / samplingFreq;
corrSin[f][g] += sampleTemp[g][i] * sin(angle);
corrCos[f][g] += sampleTemp[g][i] * cos(angle);
```

**ใหม่:** ความถี่ของ LED ทุกดวงเป็นพหุคูณของ 100 Hz เฟสจึงวนซ้ำทุก 25000/100 = 250 ตัวอย่าง ตาราง sin/cos 250 ค่า (คูณ 2¹⁴ ไว้) จึงใช้ได้กับทุกดวง แค่ก้าวทีละ `Fref/100` ช่อง
```cpp
const int32_t s = sinQ[idx], c = cosQ[idx];
accSin[g] += x * s;          // จำนวนเต็มล้วน
accCos[g] += x * c;
idx += step;                 // step = Fref / 100
if (idx >= LUT_N) idx -= LUT_N;
```

- ครึ่งหลังของตารางคือครึ่งแรกที่กลับเครื่องหมาย ผลรวมของตารางจึงเป็น 0 พอดี และแสง DC หักล้างหมดจริง
- **ข้อจำกัด:** ถ้าเปลี่ยนความถี่ของ LED ต้องเป็นพหุคูณของ 100 Hz และ `N` ต้องเป็นพหุคูณของ 250 (`tests/firmware-math.test.js` ตรวจทั้งสองข้อ)

### 3.3 Path loss: เมทริกซ์ BLA → float ตรง ๆ

**เก่า:** ทุกครั้งที่เรียก สร้างเวกเตอร์และเมทริกซ์หมุนใหม่ และใช้ `pow()`
```cpp
BLA::Matrix<3, 3> Omega0 = { cos(t0), sin(t0), 0.0, -sin(t0), cos(t0), 0.0, 0.0, 0.0, 1.0 };
tmp = ~(pk - p0) * (Omega0 * vl) / dk;
return (m + 1) * pow(cosPhikl, m) * cosPsikl / pow(dk, 2);
```

**ใหม่ (`pathLossCS`, บรรทัด 234):** สูตรเดิมแต่กระจายเป็นการคูณบวกธรรมดา รับ cos θ และ sin θ ที่คำนวณไว้แล้วเข้ามา
```cpp
const float w0 =  c0 * v(l, 0) + s0 * v(l, 1);   // = Omega0 * vl
const float w1 = -s0 * v(l, 0) + c0 * v(l, 1);
const float cosPsikl = -(dx * w0 + dy * w1 + dz * w2) / dk;
return (m + 1) * cosPhikl * cosPsikl / (dk * dk);  // m = 1
```

ผลของ 3.2 และ 3.3 รวมกัน (branch `-realtime`, วัดบนบอร์ด): รอบละ 330 ms → **119 ms (8.4 Hz)** แบ่งเป็นเก็บสัญญาณ 100 + demod 12 + EKF 6.9 ms พอเพิ่ม 3.1 ช่วงรอเก็บสัญญาณก็หายไป ได้ **50 ms (20 Hz)** แบ่งเป็น wait 20.1 + demod 19.0 + EKF 10.2 ms (demod และ EKF ช้าลงเพราะ interrupt เก็บสัญญาณทำงานตลอด)

### 3.4 แบบจำลอง: เพิ่ม `PD_GAIN` และ `RSS_OFFSET`

ตอน calibrate พบว่า:
- PD0 อ่านได้สูงกว่าแบบจำลอง 12–21% ทุก LED ส่วน PD1 และ PD2 ต่ำกว่า PD0 ราว 8–9% → เพิ่ม `PD_GAIN = {1.000, 0.917, 0.906}`
- LED ที่ไกลกว่า 1.25 m อ่านได้สูงกว่าแบบจำลองราว 21% น่าจะเป็นแสงสะท้อนกับ noise floor → เพิ่ม `RSS_OFFSET = 0.0689`

หลังเพิ่มทั้งสองค่า ความคลาดของแบบจำลองลดจาก 12–18% เหลือ 8–10% และ x/y บน PC (leave-one-out) ลดจาก 5.9 เป็น 3.6 cm ค่าทั้งหมด fit ร่วมกันด้วย `fitModel()` ใน `calib-model.js` ซึ่งต้องตรงกับ firmware เสมอ (test ตรวจ)

`RSS_OFFSET` ไม่มีผลต่อ Jacobian เพราะบวกเท่ากันทั้งสองฝั่งของผลต่าง

### 3.5 แกน z

- เพิ่ม z และ vz ไว้ท้าย state เพื่อให้ index ของ x, y, θ ไม่เปลี่ยน
- `ESTIMATE_Z = true` เปิดการประมาณ z ถ้าตั้งเป็น `false` จะบังคับ z = 0
- จำกัด z ไว้ในช่วง `Z_MIN = 0` ถึง `Z_MAX = 0.80` m (ไม่ให้ต่ำกว่าพื้น และไม่ให้เข้าใกล้ LED จนแบบจำลองระเบิด) ถ้าชนขอบจะตั้ง vz เป็น 0
- **ข้อจำกัด:** z สูงขึ้น 1 cm ทำให้ RSS เปลี่ยนแค่ราว 0.8% ถ้าแบบจำลองคลาด 5% z จะเพี้ยนราว 6 cm หน้าเว็บจึงมีปุ่ม "ตั้งศูนย์ z"

### 3.6 จูน EKF: `T` และ `Q`

**เก่า:** `T = 0.2` คงที่ แต่รอบจริงยาวราว 0.33 s ทำให้ความเร็วที่ประมาณได้เพี้ยน ส่วน `Q = 1e-6` น้อยจน filter เชื่อแบบจำลองความเร็วคงที่มากเกินไป พอหุ่นหยุด ตำแหน่งจึงวิ่งเลยไปราว 8 cm

**ใหม่:**
```cpp
T = (time1 - lastUpdate) / 1000.0f;            // เวลารอบจริง ≈ 0.05 s
Q(i, i) = Q0[i] * T / T_REF;                   // Q0 = 1e-4, T_REF = 0.33 s
```
การปรับ `Q` ตาม `T / T_REF` ทำให้ noise ต่อวินาทีเท่าเดิมไม่ว่ารอบจะเร็วขึ้นเท่าไร ผลจำลองบน PC: วิ่งเลยไป 3–4 cm และนิ่งใน 2–3 s (ยังไม่ได้ทดสอบ `move_straight` ซ้ำบนบอร์ด)

### 3.7 Correct ทีละค่า (`ekfUpdateSequential`)

เพราะ `R` เป็นเมทริกซ์ทแยง จึงแยกการ correct ด้วยเวกเตอร์ 27 ค่าออกเป็น correct ทีละค่าได้ ผลเท่ากันทางคณิตศาสตร์ และไม่ต้อง inverse เมทริกซ์ 27×27 (แต่ละค่าหารด้วยเลขตัวเดียว)

```
สำหรับ RSS แต่ละค่า i (เฉพาะ LED ที่เปิด), h = แถว i ของ J:
  S = h·P·hᵀ + σ²
  K = P·hᵀ / S
  x = x + K·(z_i − ẑ_i − h·(x − x̂⁻))    // ยังใช้แบบจำลองที่ linearize ที่ x̂⁻
  P = (I − K·h)·P·(I − K·h)ᵀ + σ²·K·Kᵀ
```
ตั้ง `EKF_SEQUENTIAL = false` เพื่อกลับไปใช้สูตรเดิมไว้เทียบได้

### 3.8 Output และ WiFi

- ทุกอย่างพิมพ์ผ่าน `out` (class `Out`) ซึ่งส่งไป `Serial` และตัดเป็นบรรทัดแล้วใส่ใน ring 8 KB สำหรับ WiFi
- Pico W เปิด AP ที่ `192.168.42.1` มี path ดังนี้:
  - `GET /events` ส่งบรรทัดแบบ Server-Sent Events
  - `GET /cmd?c=LED%201%200` ส่งคำสั่งแบบเดียวกับ serial
  - `GET /` ตอบ "RA robot ok"
- WiFi ทำงานบน core 0 เท่านั้น และ `wifiPoll()` ไม่บล็อก จึงเรียกได้ตอนรอช่วงข้อมูลถัดไป
- ปิด WiFi ได้ด้วย `#define USE_WIFI 0` (ใช้ได้กับ Pico ที่ไม่มี W)
